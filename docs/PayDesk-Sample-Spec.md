# PayDesk Sample

## Introduction and intent

This sample is meant to illustrate the following points:

* Even if applications are built on Windows/MacOS/Linux, they are usually deployed via Linux containers, and increasingly via orchestration systems like Kubernetes
* Linux has some runtime security features, that can be used to keep the production enviroment safe, including:
  * uid/gid/filesystem security
  * Linux capabilities
  * seccomp
  * AppArmor
* These security features are aggressively used and audited in production environments. Containers and orchestration systems surface them, and encourage their use
* These features can help secure some aspects of applications, even if the applications themselves have security concerns
* Sometimes, security is loosened because when an application is run for the first time in a production environment, it fails because it hits these security features. For example, if an application crashes because it cannot write a file, the runtime user id is changed to root (0), which usually solves the crashing problem but introduces a potential security hole

The sample was designed to be a realistic-looking application on which these security features can be applied, to see what happens.

## Basic specifications

The application, named PayDesk, looks like a typical HR app. It is to be created using .NET 10 SDK, ASP.NET Core, Razor Pages, and EF Core with a Postgres backend. The following functionalities are available:

* Simple login. There are two categories of users: regular and admin. Admin can create additional users. ASP.NET Identity can be used for this, unless a simpler alternative exists.
* A Dashboard, where all users can upload expense report files. For simplicity, these can be CSV files in the format: <YYYY-MM-DD Date of Expense>,<Description of Expense>,<CurrencyAmount>. A single user can upload any number of expense report files in a month. The files are uploaded to a directory, and a database entry is maintained, marking the file status as 'Pending'. The dashboard should show all pending files for the current user.
* Admin users can trigger a consolidation process for a month, which will launch a separate executable that will calculate per-user totals for that month and record that in the database. It should also set the status of processed files to 'Processed', at which point they no longer appear on the dashboard. Finally, the consolidation process should generate payslip files for the month, which are PDF files which show the expenses and the total payout. Once a particular month's consolidation process runs, no further expenses can be logged for that month. 
* Users should also be able to download their payslips (generated by the consolidation process), for a given month.
* There should be a application status page, available to all users, which would ping the backend database server and indicate all is well if the ping succeeds, or show a red status if it fails.

While this is a demo sample, it should look like a real application. To that end:

* The default tools should be used as much as is possible. Any dependencies should be managed  properly.
* Best practices should be used for project, solution and directory structures. For example, the consolidation process should be a separate project that produces a standalone executable, which can be triggered asynchronously from the ASP.NET application by admin users only.
* Any setup and startup instructions should be included, especially for the database back-end.
